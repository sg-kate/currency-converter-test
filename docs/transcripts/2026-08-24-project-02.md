#!/bin/sh
# Runs inside the wordpress:cli container as the scheduler for the whole stack.
# DISABLE_WP_CRON is true in wp-config.php, so this loop is the only thing that
# makes scheduled events fire. Deliberately NOT `set -e`: a failing tick (WordPress
# not installed yet, database restarting) must not kill the container.

interval="${CRON_INTERVAL:-60}"
echo "[cron] loop started, interval ${interval}s"

while true; do
	if wp core is-installed --quiet 2>/dev/null; then
		wp cron event run --due-now 2>&1 | sed 's/^/[cron] /'
	else
		echo "[cron] WordPress not installed yet, waiting"
	fi
	sleep "${interval}"
done

site with a single `make bootstrap`. The script is idempotent, so re-running it
after a pull or a config change is safe.

Notable choices:

- MariaDB 10.11 rather than MySQL. MySQL 8.0.19+ dropped integer display width,
  so `bigint(20)` in a schema definition no longer matches the `bigint` that
  DESCRIBE reports, and dbDelta() then emits an ALTER on every plugin activation.
- Core is bind-mounted to ./wordpress rather than kept in a named volume, so it
  is readable on the host and an editor can index it. The directory is gitignored
  and disposable; `make reset` empties it from a root container, since the files
  are written as uid 33.
- The WordPress environment block is shared across the wordpress, wpcli and cron
  services through a YAML anchor. The image's wp-config.php eval()s
  WORDPRESS_CONFIG_EXTRA at runtime, so a container without that block would run
  with DISABLE_WP_CRON and WP_HOME undefined. bootstrap.sh asserts the constants
  via `wp eval`, because `wp config get` parses the file statically and cannot
  see them. The defines are guarded, as WP-CLI loads wp-config.php twice.
- WP-Cron is disabled and a cron service runs due events every 60s: wp-cron.php
  only fires on page loads, so on a development site nobody visits scheduled
  events would never run at all.
